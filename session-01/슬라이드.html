NETWORK FUNDAMENTALS LAB — 00

온램프: 비트 하나가 네트워크를 가른다

본격적인 장애 실습 전, IP/서브넷을 비트 단위로 읽는 법과 MAC·IP의 역할 차이를 질문 → 추측 → 실습 검증 → 피드백 순서로 다졌다.

10.10.10.1/24 — 앞 24비트는 고정(네트워크), 뒤 8비트는 자유(호스트)

↓ 스크롤 또는 ↓ 키로 다음 슬라이드

01 핵심 개념

이 장에서 확인한 네 가지

비트와 옥텟

스위치 하나 = 비트(0/1). 8개를 묶으면 2⁸=256가지 패턴이 나오고, 그걸 사람이 읽기 쉽게 0~255로 번역한 게 옥텟이다.

마스크의 진짜 기준

/N은 "앞 N비트가 같은가"가 전부다. 8의 배수(/8 /16 /24)일 때만 옥텟 단위로 단순화되고, /26 /30은 옥텟 안쪽에서 갈린다.

L2 vs L3 — 왜 둘 다 필요한가

IP(L3)는 "어느 네트워크로" 갈지, MAC(L2)는 "이 전선 위 누구에게" 건넬지를 정한다. 전선은 IP를 모른다 — 그래서 ARP가 번역한다.

MAC은 장비가 아니라 인터페이스의 주소

노트북 한 대도 Wi-Fi·이더넷·썬더볼트 칩마다 MAC이 다르다. 그걸 대표하는 숨은 "시스템 MAC"은 존재하지 않는다.

02 직접 확인한 것 — 서브넷 계산

자유비트 = 32 − 마스크

/30 사용 가능 호스트 2개

자유비트 2개 → 2²=4가지 → 예약 2개(네트워크·브로드캐스트) 제외 → 10.5.2.0network / 10.5.2.3broadcast, 쓸 수 있는 건 .1 .2

/28 사용 가능 호스트 14개

자유비트 4개 → 2⁴=16가지 → 예약 2개 제외 → 10.5.2.0network / 10.5.2.15broadcast, 쓸 수 있는 건 .1~.14

03 직접 확인한 것 — ARP

IP만으론 프레임을 못 보낸다

$ ip neigh · tcpdump arp (containerlab h1 ↔ h2 직결)

# ping 전: ARP 테이블 비어있음
# ARP, Request who-has 10.0.0.2 tell 10.0.0.1
# ARP, Reply   10.0.0.2 is-at aa:c1:ab:46:f1:c0
# ping 후: 10.0.0.2 dev eth1 lladdr aa:c1:ab:46:f1:c0 REACHABLE

이더넷 프레임은 목적지 MAC이 있어야 전선 위로 나간다 — 스위치·NIC는 IP를 모른다. 그래서 ping 한 번에도 ARP 요청/응답이 먼저 오간다.

04 직접 확인한 것 — MAC 주소

MAC은 "장비 하나"가 아니라 "인터페이스 하나"

$ networksetup -listallhardwareports (맥북 실제 출력)

Wi-Fi (en0)무선 칩7c:f3:4d:ed:12:d6
Ethernet (en4)유선 어댑터5a:f2:11:a2:1f:ce
Thunderbolt 1 (en1)썬더볼트 포트36:24:9f:77:30:c0

세 MAC이 전부 다르다. 이 중 하나가 "진짜 시스템 대표 MAC"인 게 아니라, 인터페이스(칩)마다 MAC이 하나씩 있는 것뿐이다. 숨은 대표 주소는 없다.

05 헷갈렸던 부분 → 교정

세 번 틀렸고, 세 번 교정됐다

  • "/24 호스트 범위는 1~255까지"
    1~254. .0은 네트워크 주소, .255는 브로드캐스트 주소 — 둘 다 예약값.
  • "/30의 자유비트는 6개(2⁶=64)"
    자유비트 = 32−30 = 2개뿐. 2²=4가지 중 예약 2개를 빼면 호스트는 2개.
  • "MAC도 장비 전체를 대표하는 값이 따로 있다"
    인터페이스(칩)마다 MAC 1개가 전부. 숨은 "대표 MAC"은 없다.

06 한 줄 교훈

IP(L3, 전역 라우팅)와 MAC(L2, 로컬 전달)은 역할이 달라서 둘 다 필요하다. 서브넷 마스크는 비트 단위로 "앞부분이 일치하는가"가 기준이며, 8의 배수일 때만 옥텟으로 단순화된다.
