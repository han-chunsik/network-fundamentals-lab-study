## 00. 온램프

### Q1. `10.10.10.1/24`와 `10.10.10.200/24`는 같은 네트워크인가?
- 내 답변(실습 전): 같다. 24니까 10.10.10.1~255까지 같은 네트워크라고 생각함. (단, /24가 정확히 뭔지는 모르겠고, 이전에 다르게 나온 경험이 있어서 헷갈림)
- 실습 결과(python ipaddress 검증): 둘 다 network=10.10.10.0, broadcast=10.10.10.255, host_range=10.10.10.1~254 → 같은 네트워크 확인.
- 설명: `/24` = 앞 32비트 중 **앞 24비트(=3개 옥텟)**가 네트워크 부분, 나머지 8비트가 호스트. 10.10.10.1과 10.10.10.200은 앞 24비트(10.10.10)가 동일 → 같은 네트워크. "24=옥텟 3개"는 24가 8의 배수라서 생기는 우연의 일치고, 진짜 기준은 "비트 단위로 마스크 길이만큼 앞부분이 일치하는가"이다.
- 피드백: 결론(같다)은 맞음. 근거는 2곳 보완 필요 — ① 실제 호스트 가능 범위는 1~254 (0=네트워크 주소, 255=브로드캐스트 주소, 둘 다 예약값). ② "계속 다르던데"의 원인은 보통 세 번째 옥텟처럼 24비트 안에 있는 다른 부분이 달랐던 경우(예: 10.10.10.x vs 10.10.20.x) — "뒤 숫자 범위"가 아니라 "마스크 비트 수만큼 앞이 같은가"가 진짜 판단 기준.

### 기초지식: 비트 / 옥텟이란?
- 비트 = 전등 스위치 하나 (0 또는 1, 두 상태뿐).
- 옥텟 = 스위치 8개 묶음 → 8개로 표현 가능한 패턴 수 = 2^8 = 256가지 → 그걸 사람이 읽기 쉽게 0~255 숫자로 번역한 것.
- IP 주소(예: 10.10.10.1)는 옥텟 4개 = 스위치 32개.
- 마스크(/N)는 "앞에서부터 몇 개의 스위치가 같아야 같은 네트워크로 치는지"를 정함.

### 옥텟 단위 마스크 규칙 (8의 배수일 때만 깔끔하게 적용됨)
- `/32` = 같다.같다.같다.같다
- `/24` = 같다.같다.같다.자유
- `/16` = 같다.같다.자유.자유
- `/8`  = 같다.자유.자유.자유
- (주의: `/26`, `/30` 처럼 8의 배수가 아닌 마스크는 옥텟 "안쪽"에서 경계가 끊겨서 이 표로 안 됨 → 추후 비트 단위로 다시 다룰 것)

### Q2. `192.168.1.100/16`과 `192.168.99.1/16`는 같은 네트워크인가?
- 내 답변(실습 전): 같은 네트워크. /16이니까 앞 2묶음(옥텟)만 같으면 됨. (옥텟 규칙을 스스로 일반화해서 적용함)
- 실습 결과(python ipaddress 검증): 둘 다 network=192.168.0.0/16 → 같은 네트워크 확인.
- 설명: /16 = 앞 16비트(2옥텟) 일치 필요, 나머지 2옥텟(세 번째·네 번째)은 자유. 세 번째 옥텟이 1 vs 99로 크게 달라도 /16에서는 무관.
- 피드백: 결론·근거 모두 정확. Q1에서 배운 "비트/마스크 기준"을 스스로 일반화해서 옥텟 단위 규칙표를 만들어 적용함 — 암기가 아니라 이해 기반 적용이 된 상태.

### Q3. `10.10.10.1/24`와 `10.10.20.2/24`는 같은 네트워크인가?
- 내 답변(실습 전): 다른 네트워크. (보너스: /16이면 10.10.10.1/16, 10.10.20.2/16 이 같아질 것이라고 추측)
- 실습 결과: /24 → 10.10.10.0/24 vs 10.10.20.0/24 (다름, 세 번째 옥텟 10≠20이 /24의 "같다" 구간 안에 있어서). /16 보너스 → 둘 다 10.10.0.0/16 (같음) — 보너스 추측도 적중.
- 설명: /24는 "같다.같다.같다.자유" 구간이라 세 번째 옥텟(10 vs 20)이 달라 네트워크가 갈림. /16으로 넓히면 세 번째 옥텟이 "자유" 구간으로 들어가서 같아짐.
- 피드백: 결론·보너스 추측 모두 정확. 마스크를 바꿨을 때 결과가 어떻게 달라지는지 스스로 뒤집어 검증한 것은 실제 트러블슈팅 사고방식과 동일.

### Q4. `/24`와 `/30`의 호스트 개수는?
- 내 답변(실습 전): /24=254(정답). /30=62 (2^6 사용) → 오답.
- 실습 결과(python ipaddress): /30 → network=10.5.2.0, broadcast=10.5.2.3, usable_hosts=[10.5.2.1, 10.5.2.2] → 실제는 2개.
- 설명: 자유 비트 수 = 32 − 마스크숫자. /30 → 32−30=2개 자유비트 → 2^2=4가지 조합 → 예약 2개(네트워크주소/브로드캐스트) 빼면 2개. 62는 2^6(=/26의 계산)을 잘못 대입한 것.
- 피드백: 공식(2^자유비트−2)은 정확히 알고 있었음. "자유 비트 수=32−마스크"를 계산할 때 30을 26처럼 다뤄서 6을 사용한 숫자 대입 실수. 공식 자체는 이해했으므로 다음엔 마스크 숫자를 32에서 빼는 단계를 다시 확인하면 됨. /30=호스트 2개는 라우터 간 1:1 링크(04장에서 재등장)에 자주 쓰임.

### Q4 재도전 (/28 호스트 개수)
- 내 답변(실습 전): 자유비트 32-28=4개 → 2^4=16가지 → 예약2개 빼면 14개.
- 실습 결과(python ipaddress): network=10.5.2.0, broadcast=10.5.2.15, usable=14개(10.5.2.1~14) → 정확히 일치.
- 설명: /30(그림으로 재학습) → /28도 같은 공식 적용. 마스크가 클수록(숫자가 큼) 자유비트가 적어서 네트워크가 좁아짐(호스트 적음) — 숫자 크기와 네트워크 크기가 반비례라는 점이 헷갈리기 쉬움. 실무에서는 필요한 장비 수에 맞춰 마스크를 고름 (/30=라우터 1:1 링크, /28=소규모 팀, /24=일반 사무실).
- 피드백: 완벽. 자유비트→조합수→예약제외 전 과정 정확. /30에서의 숫자 대입 실수가 그림(표)으로 본 뒤 바로 교정됨 — 추상 공식보다 구체적 비트 그림이 이 사람에게 더 잘 먹힘(다음에도 헷갈리면 표로 다시 그려줄 것).

### Q5. IP 주소와 MAC 주소, 왜 두 개나 필요한가?
- 내 답변(실습 전): MAC은 하드웨어 고정값, IP는 유동적(DHCP로 MAC에 IP 고정하기도 함).
- 실습 결과(containerlab h1↔h2 직결): ping 전 `ip neigh`는 비어있음 → ping 시도 시 tcpdump로 `ARP Request who-has 10.0.0.2 tell 10.0.0.1` → `ARP Reply 10.0.0.2 is-at aa:c1:ab:46:f1:c0` 캡처됨 → 그 후에야 ping 성공, ARP 테이블에 매핑 채워짐.
- 설명: 이더넷 프레임은 목적지 MAC이 반드시 있어야 전선 위로 나갈 수 있음(스위치/NIC는 IP를 모름). IP만 알아도 실제 전송 불가 → ARP로 IP를 MAC으로 번역해야 함. IP(L3)=전역적 네트워크 간 주소, MAC(L2)=로컬 세그먼트 안 물리적 전달 주소. 역할이 다르기 때문에 둘 다 필요.
- 피드백: 답변한 사실(고정 vs 유동)은 맞지만 "왜 두 개가 필요한가"의 답은 아니었음 — 그건 성격 차이 설명이고, 진짜 이유는 레이어별 역할 분리. ARP request/reply를 직접 캡처해서 "IP만으론 프레임을 못 보낸다"는 걸 눈으로 확인함. (01장 ARP의 예고편)

#### Q5 확장: MAC은 "장비 하나"가 아니라 "인터페이스 하나"의 주소
- 내 추측: Wi-Fi랑 랜선 MAC이 다를 것 같고, "진짜 시스템 MAC"도 별도로 있을 것 같다.
- 실습 결과(맥북에서 `networksetup -listallhardwareports`): Wi-Fi(en0)=7c:f3:4d:ed:12:d6, 썬더볼트 포트들마다 다른 MAC, bridge0는 en1의 MAC을 그냥 빌려 씀.
- 설명/피드백: Wi-Fi≠랜선 MAC은 맞음. 하지만 "별도의 시스템 MAC"은 오개념 — 숨은 대표 MAC은 없고, **인터페이스(칩)마다 MAC 1개**가 전부. 시리얼번호/UDID는 MAC과 다른 개념(통신에 안 쓰임).
- 사용자 최종 정리(맞음): "MAC은 하드웨어 전체를 대표하는 게 아니라, 그 하드웨어가 가진 인터페이스의 주소다 — 전기신호를 받을 주소." ✅ 완벽하게 교정됨.
